# Remote execution providers

`registerRemoteExecutionProviders(registry)` registers `modal/v1`, `daytona/v1`, and `e2b/v1` as execution services. Each implements `RuntimeExecutor`; orchestration, task management, identity, and runtime protocols remain separate. All providers run the same worker with the selected coding-agent driver, including runtime drivers registered by installed worker plugins.

## Configuration

Provider options are inline fields under `execution.provider`, alongside `type`. These provider-owned keys use camelCase and are not normalized by the core parser.

| Field | Meaning |
| --- | --- |
| `repository` | Required HTTPS Git URL without embedded credentials, query, or fragment |
| `ref` | Committed branch, tag, or commit to check out; defaults to cloned `HEAD` |
| `timeoutMs` | Whole-task deadline, including provisioning; defaults to 15 minutes, maximum 24 hours; cloud account limits may be lower |
| `envSecrets` | Map of worker environment variable names to host secret resolver names; no automatic host environment forwarding |
| `workerCommand` | Argument array; defaults to `['node', '/opt/harnessfile/dist/src/services/execution/worker.js']` |
| `workerPlugins` | Explicit installed plugin modules or absolute paths loaded inside the image; defaults to none |
| `image`, `app` | Modal: required OCI registry image and optional app name (default `harnessfile`) |
| `snapshot` | Daytona: required prepared snapshot name |
| `template` | E2B: required prepared template ID/name |
| `tokenIdSecret`, `tokenSecretSecret` | Modal API credential references, defaulting to `MODAL_TOKEN_ID` and `MODAL_TOKEN_SECRET` |
| `apiKeySecret` | Daytona/E2B API credential reference, defaulting to `DAYTONA_API_KEY` / `E2B_API_KEY` |
| `apiUrl`, `target` | Optional Daytona API URL and region target |

Optional SDKs are loaded only for the selected provider and resolved from the harness workspace first, then the CLI installation. Install `modal`, `@daytona/sdk`, or `e2b` on the host. A missing package reports its install command. Worker images do not need these SDKs.

The adapters were checked against the published npm packages `modal@0.10.1`, `@daytona/sdk@0.218.0`, and `e2b@2.51.0`. Verification included the packages' declarations and implementations and a compile-only fixture covering creation options, file upload, streaming, process completion, and deletion. Daytona's inherited command request/response fields were checked against `@daytona/toolbox-api-client@0.218.0`. Pin these SDK versions for a reproducible initial deployment; mocked tests and declaration checks do not replace a credentialed cloud smoke test. No live cloud test has been performed.

## Worker protocol

The host provisions a sandbox and writes a JSON request outside the checkout. It runs `workerCommand` with that request file as its final argument. The worker reads and deletes the request, clones the configured repository, and passes the supplied normalized IR to `RuntimeDispatcher`. The image must include Node.js, Git, the compiled worker, and the runtime CLI(s) selected by the harness. A host plugin is not automatically present remotely; install and explicitly name worker plugins separately. Runtime command paths refer to the image filesystem.

Stdout carries newline-delimited `{version: 1, type: 'event', event: RuntimeEvent}` envelopes followed by exactly one `{version: 1, type: 'result', result: RuntimeTaskResult}`. Stderr is not forwarded because SDK/command errors may contain credentials. The host validates envelopes, rejects incomplete streams, and limits frames to 16 MiB. Runtime errors return a safe generic message. Plugins must keep stdout reserved for the worker protocol. Provider SDK transport exceptions are redacted before returning a failed result.

The worker exports changes relative to the checkout's original commit, including subsequent commits and untracked nonignored files, as `metadata.workspacePatch` and `metadata.workspaceBaseCommit` (4 MiB maximum patch). Export failure is explicit in `metadata.workspaceExportFailed` and a warning event. Apply artifacts only through an intentional downstream operation. No patch is automatically applied on the host. New tasks clone the configured ref again; there is no shared filesystem or implicit branch handoff. For durable repository work, the agent must push a branch before exiting.

`HARNESSFILE_GIT_TOKEN` enables a temporary Git credential helper for private clone/push. It defaults to username `x-access-token`; supply `HARNESSFILE_GIT_USERNAME` for other Git hosts, such as `oauth2` on GitLab. The token stays in the sandbox environment and never enters a URL or Git config. Coding-agent authentication (for example `ANTHROPIC_API_KEY`) is independently mapped in `envSecrets`. Provider API credentials are resolved on the host and are not forwarded to the worker. Outputs generated by an agent can still contain any secret it has been given; keep the worker's credential scope minimal.

## Lifecycle and limits

Every task uses an ephemeral sandbox. Completion, failure, timeout, abort, and environment shutdown trigger termination/deletion. A sandbox whose creation finishes after cancellation is also destroyed; `close()` waits for that cleanup before closing its SDK client. Cleanup failures appear in result metadata where available and are raised by `close()`; provider lifetime/TTL settings remain the fallback if the host process disappears. Daytona TTL rounds up to whole minutes. Infrastructure provisioning is subject to SDK request timeouts. Cancellation terminates the entire per-task sandbox.

Resume requests emit a warning and start fresh. Results deliberately omit resume pointers because the sandbox no longer exists. These adapters do not provide durable orchestration, ingress webhooks, scheduling, image publishing, cross-task workspace persistence, or automatic PR creation. Those responsibilities belong to the selected orchestration/task services and the configured agent's work. No live cloud resources are created by the tests.
