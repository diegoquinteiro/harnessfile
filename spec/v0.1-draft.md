# Harness Spec v0.1 — Draft

## What is this?

A vendor-neutral, declarative specification for defining AI agent harnesses — the operational scaffolding around agents. The spec defines **how agents are orchestrated, protected, evaluated, and triggered** — not the agents themselves.

Agents are black boxes. The harness is everything around them.

## Design principles

1. **Flat over nested** — max 3 levels of indentation. If you need more, something is wrong.
2. **Defaults over config** — works with the minimum, override only what you need.
3. **Implicit → conventional → explicit** — zero config for simple cases, conventions for common cases, explicit declarations only when needed.
4. **Interfaces over implementations** — the spec defines contracts (gate, eval, trigger), providers implement them. Swap providers without changing the harness.
5. **The spec is the graph, providers are the nodes** — the spec owns orchestration and rules. Providers own execution.

## Architecture

```

│                harness.yaml                   │

│  ┌─────────┐  ┌──────┐  ┌──────┐  ┌───────┐ │
│  │ agents  │  │ gates │  │ evals│  │trigger│ │

│       │           │         │          │      │
└───────┼───────────┼─────────┼──────────┼──────┘
        ▼           ▼         ▼          ▼
┌──────────────────────────────────────────────┐
│                 Providers                     │
│                                               │
│  agent:  default, oracle-agent-spec, crewai,  │
│          a2a, langgraph, ...                  │
│  gate:   slack, teams, email, web-ui, ...     │

│  memory:  postgres, redis, pinecone, ...      │
│                                               │
└──────────────────────────────────────────────┘
```

Every component is a provider — including agents. The spec does not know how to execute anything. It only knows the graph and the contracts.

## Provider model

Providers are plugins that implement standard interfaces. The spec defines what fields each component type must support. Providers may accept extra fields prefixed with `x-`.

```yaml
providers:
  gate: slack/v1
  eval: pytest/v1
```

When no provider is declared:
- **Agents**: use the built-in simple agent spec (model + instructions + tools)
- **Other components**: runtime resolves from conventions (e.g., `channel: "#approvals"` implies Slack)

The built-in agent spec is itself a provider — it has no special status in the spec. It is simply loaded by default to reduce friction.

## Skills

Skills are reusable bundles of instructions, tools, and evals that can be shared across agents. They allow defining a capability once and attaching it to multiple agents.

```yaml
skills:
  code-review:
    instructions: Review code for quality, security, and adherence to patterns.
    tools:
      - mcp: ./tools/github.json
    eval:
      metric: checklist
      expect: [security, patterns, tests]

  web-research:
    instructions: Search and synthesize information from the web.
    tools:
      - mcp: ./tools/web-search.json

agents:
  senior-dev:
    model: anthropic/claude-sonnet-4-6
    instructions: Senior full-stack developer.
    skills: [code-review, web-research]

  junior-dev:
    model: anthropic/claude-sonnet-4-6
    instructions: Junior frontend developer.
    skills: [code-review]
```

When an agent references a skill:
- The skill's `instructions` are appended to the agent's instructions
- The skill's `tools` are merged into the agent's tools
- The skill's `eval` is applied when the agent executes that capability

Skills are a spec-level concept — they work regardless of the agent provider.

## Standard interfaces

### Agent

```yaml
# Fields the spec guarantees for the default provider:
model: string           # provider/model-name (e.g., anthropic/claude-sonnet-4-6)
instructions: string    # system prompt
tools: list             # MCP servers, functions, APIs
skills: list            # references to shared skills
```

### Gate

```yaml
approve: human | auto   # who approves
channel: string         # where to send (e.g., "#approvals", "manager@co.com")
timeout: duration       # how long to wait
fallback: reject | approve | escalate
```

### Eval

```yaml
metric: string          # what to measure (llm-judge, tests-pass, coverage, custom)
pass: number | string   # threshold to pass (0.8, "80%", "approved")
prompt: string          # for llm-judge: the evaluation prompt
dataset: string         # for batch evals: path to dataset file
```

### Trigger

```yaml
event: string           # what starts the harness (webhook, cron expression, event source)
filter: string          # optional filter on the event
```

### Observability

```yaml
tracing: string         # provider name or "off"
metrics: string         # provider name or "off"
```

### Memory

```yaml
backend: string         # storage backend
ttl: duration           # time to live
```

## Coordination patterns

The spec supports five coordination patterns for steps:

### Router

One agent classifies input, output maps to the next step.

```yaml
steps:
  classify:
    type: router
    agent: classifier
    routes:
      feature: research
      bug: bug-pipeline
      refactor: refactor-pipeline
```

### Pipeline

Sequential steps connected by `next:`.

```yaml
steps:
  research:
    agent: researcher
    next: spec

  spec:
    agent: spec-writer
    next: plan

  plan:
    agent: planner
    next: review
```

### Parallel

Multiple branches execute simultaneously. Optional shared context.

```yaml
steps:
  implement:
    type: parallel
    shared-context: true
    branches:
      frontend:
        agent: frontend-dev
      backend:
        agent: backend-dev
      tests:
        agent: test-dev
    next: review
```

### Orchestrator

An agent dynamically spawns sub-agents from a pool. The harness defines constraints, the agent decides what to spawn.

```yaml
steps:
  research:
    type: orchestrator
    agent: researcher
    pool: [web-search, code-search, doc-search]
    max-agents: 5
    timeout: 10m
    next: spec
```

The orchestrator is the only pattern where the graph is not fully known at parse time. The agent builds the graph at runtime within the constraints the harness defines.

### Eval-loop

An agent produces output, an eval checks it, the loop repeats until the eval passes or max iterations are reached.

```yaml
steps:
  frontend:
    type: eval-loop
    agent: frontend-dev
    eval:
      - metric: tests-pass
      - metric: coverage
        pass: 80%
    max-iterations: 3
```

## Cross-cutting concerns

Evals, hooks, and observability can be applied at any level:

- **Global** — applies to all steps
- **Per-step** — overrides or extends global

Per-step config merges with global (additive, not replacing).

```yaml
# Global
observability:
  tracing: langfuse

hooks:
  on-error: slack:#alerts

steps:
  spec:
    agent: spec-writer
    # Per-step eval
    eval:
      metric: llm-judge
      prompt: "Is this spec complete?"
      pass: 0.8
    # Per-step hook (adds to global, does not replace)
    hooks:
      after-step: ./scripts/notify.sh
    next: plan
```

## Full example

A Jira-triggered feature pipeline with routing, orchestration, parallel implementation, eval loops, and human gates.

```yaml
harness: "0.1"
name: jira-feature-pipeline

providers:
  trigger: jira/v1
  gate: slack/v1
  observe: langfuse/v1

trigger:
  event: ticket-created
  filter: "project = ENG AND type = Story"

observability:
  tracing: langfuse

skills:
  coding:
    instructions: Write clean, well-structured code following project conventions.
    tools:
      - mcp: ./tools/github.json

  code-review:
    instructions: Review code for quality, security, and adherence to patterns.
    tools:
      - mcp: ./tools/github.json
    eval:
      metric: checklist
      expect: [security, patterns, tests]

agents:
  classifier:
    model: anthropic/claude-haiku-4-5
    instructions: Classify the Jira ticket as feature, bug, or refactor.

  researcher:
    model: anthropic/claude-sonnet-4-6
    instructions: Research the problem space thoroughly.

  web-search:
    model: anthropic/claude-sonnet-4-6
    instructions: Search the web for relevant information.
    tools:
      - mcp: ./tools/web-search.json

  code-search:
    model: anthropic/claude-sonnet-4-6
    instructions: Search the codebase for relevant patterns.
    tools:
      - mcp: ./tools/code-search.json

  spec-writer:
    model: anthropic/claude-sonnet-4-6
    instructions: Write a detailed technical spec.

  planner:
    model: anthropic/claude-sonnet-4-6
    instructions: Create an implementation plan with milestones and risks.

  frontend-dev:
    model: anthropic/claude-sonnet-4-6
    instructions: Implement frontend changes following React patterns.
    skills: [coding, code-review]

  backend-dev:
    model: anthropic/claude-sonnet-4-6
    instructions: Implement backend changes following our API patterns.
    skills: [coding, code-review]

  test-dev:
    model: anthropic/claude-sonnet-4-6
    instructions: Write comprehensive tests for the implementation.
    skills: [coding]

  merger:
    model: anthropic/claude-sonnet-4-6
    instructions: Merge all branches and resolve conflicts.
    skills: [coding]

steps:
  classify:
    type: router
    agent: classifier
    routes:
      feature: research
      bug: bug-pipeline
      refactor: refactor-pipeline

  research:
    type: orchestrator
    agent: researcher
    pool: [web-search, code-search]
    max-agents: 5
    timeout: 10m
    next: spec

  spec:
    agent: spec-writer
    eval:
      metric: llm-judge
      prompt: "Is this spec complete and actionable?"
      pass: 0.8
    next: plan

  plan:
    agent: planner
    next: plan-review

  plan-review:
    type: gate
    approve: human
    channel: "#approvals"
    timeout: 1h
    fallback: reject
    next: implement

  implement:
    type: parallel
    shared-context: true
    branches:
      frontend:
        type: eval-loop
        agent: frontend-dev
        eval:
          - metric: tests-pass
          - metric: lint-pass
        max-iterations: 3
      backend:
        type: eval-loop
        agent: backend-dev
        eval:
          - metric: tests-pass
          - metric: coverage
            pass: 80%
        max-iterations: 3
      tests:
        type: eval-loop
        agent: test-dev
        eval:
          - metric: tests-pass
        max-iterations: 3
    next: code-review

  code-review:
    type: gate
    approve: human
    channel: "#code-review"
    timeout: 2h
    fallback: reject
    next: merge

  merge:
    agent: merger

## v0.1 scope

### In scope

- Harness spec with steps, agents, and coordination patterns (router, pipeline, parallel, orchestrator, eval-loop)
- Skills as reusable capability bundles (instructions + tools + evals) shared across agents
- Gates (human and automated)
- Eval pluggable at any level (global, per-step, per-loop)
- Hooks pluggable at any level
- Trigger definition
- Observability definition
- Memory definition
- Provider model for all components
- Standard interfaces for each component type
- Built-in simple agent spec as default provider
- Support for external agent formats via providers (oracle-agent-spec, crewai, a2a, etc.)
- JSON Schema for validation

### Out of scope (future versions)

- Runtime implementation / reference runtime
- Provider SDK / provider development kit
- Agent-to-agent communication protocol (use A2A)
- Tool protocol (use MCP)
- Authentication / secrets management
- Versioning and migration between spec versions
- Visual editor / GUI tools
```
