# Harnessfile Spec v0.1 — Draft

## What is this?

A vendor-neutral, declarative specification for defining AI agent harnesses — the operational scaffolding around agents. The spec defines **how agents are orchestrated, protected, evaluated, and triggered**.

Agents can be defined inline for convenience or referenced from external specs (Oracle Agent Spec, Microsoft AgentSchema, etc.) via providers. The harness owns the graph and the rules — not the agent internals.

## Design principles

1. **Flat over nested** — max 3 levels of indentation. If you need more, something is wrong.
2. **Defaults over config** — works with the minimum, override only what you need. Every field has a sensible default.
3. **Progressive disclosure** — start with the minimum. Add fields, providers, and overrides only as complexity demands. A 4-line Harnessfile works.
4. **Interfaces over implementations** — the spec defines contracts (gate, eval, trigger), providers implement them. Swap providers without changing the harness.
5. **The spec is the graph, providers are the nodes** — the spec owns orchestration and rules. Providers own execution.

## Minimal example

A valid harness can be as small as this:

```yaml
harnessfile: "0.1"
agents:
  my-agent:
    model: anthropic/claude-sonnet-4-6
    instructions: Do something useful.
```

Three concepts: version, agents map, one agent definition. Everything else is optional.

## Growing the harness

Add a trigger and a two-step pipeline:

```yaml
harnessfile: "0.1"

trigger:
  event: webhook

agents:
  researcher:
    model: anthropic/claude-sonnet-4-6
    instructions: Research the problem space thoroughly.
    tools:
      - mcp: ./tools/web-search.json

  writer:
    model: anthropic/claude-sonnet-4-6
    instructions: Write a detailed report from the research.

steps:
  research:
    agent: researcher
    next: write

  write:
    agent: writer
```

Add a human gate and an eval:

```yaml
harnessfile: "0.1"

trigger:
  event: webhook

agents:
  researcher:
    model: anthropic/claude-sonnet-4-6
    instructions: Research the problem space thoroughly.
    tools:
      - mcp: ./tools/web-search.json

  writer:
    model: anthropic/claude-sonnet-4-6
    instructions: Write a detailed report from the research.

steps:
  research:
    agent: researcher
    next: review

  review:
    type: gate
    approve: human
    provider: slack/v1
    channel: "#approvals"
    timeout: 1h
    fallback: reject
    next: write

  write:
    agent: writer
    eval:
      - metric: llm-judge
        prompt: "Is this report complete and well-structured?"
        pass: 0.8
    max-iterations: 3
```

## Architecture

```
+-------------------------------------------------+
|                 Harnessfile                      |
|           (orchestration + rules)                |
|                                                  |
|  +--------+ +------+ +------+ +-------+ +-----+ |
|  | agents | | gates| | evals| |trigger| |security|
|  +---+----+ +--+---+ +--+---+ +--+----+ +--+--+ |
|      |         |        |        |          |    |
+------+---------+--------+--------+----------+----+
       v         v        v        v          v
+-------------------------------------------------+
|                  Providers                       |
|                                                  |
|  agent:   default, oracle-agent-spec, crewai,   |
|           a2a, langgraph, ...                    |
|  gate:    slack/v1, teams/v1, email/v1, ...      |
|  eval:    pytest/v1, deepeval/v1, ...            |
|  trigger: webhook/v1, jira/v1, github/v1, ...   |
|  observe: langfuse/v1, datadog/v1, otel/v1, ... |
|  memory:  postgres/v1, redis/v1, pinecone/v1,...|
|  security: owasp/v1, bedrock-guardrails/v1, ... |
+-------------------------------------------------+
```

Every component is a provider — including agents. The spec does not know how to execute anything. It only knows the graph and the contracts.

## Provider model

Providers are plugins that implement standard interfaces. They are referenced inline at their point of use, not in a top-level block.

**Shorthand** — when you only need to name the provider:

```yaml
steps:
  review:
    type: gate
    provider: slack/v1
```

**Full form** — when you need provider-specific fields:

```yaml
steps:
  review:
    type: gate
    provider:
      type: slack/v1
      x-thread: true
```

Provider names follow the `name/version` format. Namespaced providers use `namespace/name/version` for disambiguation (e.g., `harnessfile/slack/v1` vs `acme/slack/v2`).

Providers may accept extra fields prefixed with `x-` for provider-specific extensions.

When no provider is declared:
- **Agents**: use the built-in simple agent spec (model + instructions + tools)
- **Other components**: runtime resolves based on the provider type's default

The built-in agent spec is itself a provider — it has no special status in the spec. It is simply loaded by default to reduce friction.

## Standard interfaces

### Agent

```yaml
# Built-in agent provider (loaded by default):
model: string           # provider/model-name (e.g., anthropic/claude-sonnet-4-6)
instructions: string    # system prompt
tools: list             # MCP servers, functions, APIs
skills: list            # file paths to SKILL.md files
```

### Skills

Skills follow the [SKILL.md convention](https://docs.anthropic.com/en/docs/claude-code/skills) used by Claude Code, Cursor, and other agent tools. They are external files referenced by path:

```yaml
agents:
  senior-dev:
    model: anthropic/claude-sonnet-4-6
    instructions: Senior full-stack developer.
    skills:
      - ./skills/code-review.md
      - ./skills/web-research.md

  junior-dev:
    model: anthropic/claude-sonnet-4-6
    instructions: Junior frontend developer.
    skills:
      - ./skills/code-review.md
```

The harness does not define the skill format — it delegates to the SKILL.md standard. When an agent references a skill, the runtime loads the skill file and applies it according to the skill format's own rules.

This keeps agents composable without the harness reaching into agent internals.

### Gate

```yaml
approve: human          # who approves (human only — for automated checks, use eval)
provider: string        # e.g., slack/v1, teams/v1, email/v1
channel: string         # where to send (provider-specific)
timeout: duration       # how long to wait (default: 24h)
fallback: string        # reject | approve | escalate (default: reject)
```

### Eval

```yaml
metric: string          # what to measure (e.g., tests-pass, coverage, llm-judge, custom)
type: string            # code | llm | human (default: code)
pass: number | string   # threshold (e.g., 0.8, "80%", true) (default: true)
aggregate: string       # mean | min | all (default: all)
prompt: string          # for type: llm — the evaluation prompt
dataset: string         # for batch evals — path to dataset file
expected: string        # for correctness evals — field name in dataset for ground truth
```

Evals can be attached to any step. When combined with `max-iterations`, the step retries until evals pass or the limit is reached:

```yaml
steps:
  write-spec:
    agent: spec-writer
    eval:
      - metric: llm-judge
        type: llm
        prompt: "Is this spec complete?"
        pass: 0.8
      - metric: tests-pass
        type: code
        pass: true
    max-iterations: 3
    next: review
```

**Defaults:** `type: code`, `pass: true`, `aggregate: all`. A minimal eval is just `metric: tests-pass`.

### Trigger

```yaml
event: string           # what starts the harness (webhook, cron expression, event source)
filter: string          # optional filter on the event
provider: string        # e.g., jira/v1, github/v1, webhook/v1
```

### Observability

```yaml
tracing: string         # provider name (e.g., langfuse/v1) or "off" (default: off)
metrics: string         # provider name (e.g., datadog/v1) or "off" (default: off)
sampling: number        # 0.0-1.0, trace sampling rate (default: 1.0)
level: string           # calls | steps | harness (default: steps)
```

**Defaults:** tracing and metrics are off. When enabled, all steps are traced at step-level granularity with 100% sampling. Override per-step or reduce sampling for production.

### Memory

```yaml
backend: string         # provider name (e.g., postgres/v1, redis/v1)
scope: string           # thread | shared | global (default: thread)
type: string            # checkpoint | conversation | semantic (default: checkpoint)
ttl: duration           # time to live (default: none — persists indefinitely)
```

**Defaults:** `scope: thread` (isolated per harness run), `type: checkpoint` (state persistence for resume). A minimal memory config is just `backend: postgres/v1`.

### Security

```yaml
guardrails:
  input: list           # input filters (e.g., [injection-detect, pii-redact])
  output: list          # output filters (e.g., [pii-scrub, toxicity-filter])
  provider: string      # e.g., owasp/v1, bedrock-guardrails/v1
budget:
  max-tokens: number    # token ceiling per harness run (default: none)
  max-cost: string      # cost ceiling per harness run (default: none)
audit:
  destination: string   # where to log (e.g., stdout, provider name) (default: stdout)
  level: string         # actions | reasoning | full (default: actions)
```

**Defaults:** no guardrails, no budget limits, audit to stdout at actions level. All fields optional. A minimal security config:

```yaml
security:
  budget:
    max-tokens: 100000
```

### Hooks

Hooks are lifecycle callbacks that fire at specific points during harness execution. They can observe, abort, or modify execution.

**Events:**

| Event | Fires when | Available at |
|---|---|---|
| `on-start` | Harness run begins | Global only |
| `before-step` | Before a step executes | Global, per-step |
| `after-step` | After a step completes successfully | Global, per-step |
| `on-error` | A step fails | Global, per-step |
| `on-gate-pending` | A gate is waiting for approval | Global, per-step |
| `on-gate-resolved` | A gate is approved or rejected | Global, per-step |
| `on-complete` | Harness run finishes (success or failure) | Global only |

**Shorthand** — fire-and-forget notification:

```yaml
hooks:
  on-error: slack:#alerts
  after-step: ./scripts/notify.sh
```

**Full form** — when you need control:

```yaml
hooks:
  before-step:
    run: ./scripts/inject-context.sh
    can: [abort, modify]       # abort | modify (default: [] — notify only)
  after-step: ./scripts/notify.sh
  on-error:
    run: slack:#alerts
    can: [abort]
```

**Hook contract:**

Hooks receive a JSON object on stdin:

```yaml
event: string              # which event fired
step: string               # step name (null for on-start, on-complete)
status: string             # pending | success | error | gate-pending | gate-resolved
context: object            # step input context
output: object             # step output (after-step, on-complete only)
error: string              # error message (on-error only)
gate: object               # gate details (on-gate-pending, on-gate-resolved only)
```

Hooks return a JSON object on stdout:

```yaml
action: string             # continue | abort (default: continue)
output: object             # modified output (only when can: [modify])
```

If a hook returns nothing or non-JSON, `action: continue` is assumed. Shorthand hooks (no `can:` declaration) cannot abort or modify — their return value is ignored.

**Defaults:** no hooks. All events are opt-in.

## Variables

Harnesses support variable substitution using Docker Compose syntax. Variables reference environment variables with optional defaults:

```yaml
agents:
  classifier:
    model: ${CLASSIFIER_MODEL:-anthropic/claude-haiku-4-5}

steps:
  plan-review:
    type: gate
    provider: slack/v1
    channel: ${APPROVAL_CHANNEL:-#approvals}
    timeout: ${GATE_TIMEOUT:-1h}
```

**Rules:**
- `${VAR}` — required, fails if not set
- `${VAR:-default}` — uses default if not set
- Variables resolve from environment variables at harness load time
- No expressions, no conditionals, no logic — just substitution

## Data flow

By default, each step's full output is forwarded to the next step as context. This works for simple pipelines without any configuration.

For more control, steps can declare what they produce and how context is passed:

```yaml
steps:
  research:
    agent: researcher
    output: { findings: array, summary: string }
    next: spec

  spec:
    agent: spec-writer
    context: research.summary    # only receives the summary, not full output
    next: plan

  plan:
    agent: planner
    # context not specified — receives full output from spec (default)
    next: review
```

### Parallel merge

When parallel branches converge, the downstream step receives all branch outputs. The `merge` field controls how:

```yaml
steps:
  implement:
    type: parallel
    branches:
      frontend: frontend-impl
      backend: backend-impl
    merge: append              # append | synthesize | last-wins (default: append)
    next: review
```

**Defaults:** `context` receives full output from the previous step. `merge: append` concatenates parallel branch outputs. No configuration needed for simple cases.

## Error handling

Every step supports error handling fields. All are optional with safe defaults:

```yaml
steps:
  research:
    agent: researcher
    timeout: 5m               # max time for this step (default: none)
    retry: 3                  # max retry attempts on failure (default: 0)
    on-error: skip             # fail | skip | continue (default: fail)
    next: spec
```

**Defaults:** `timeout: none` (no limit), `retry: 0` (no retries), `on-error: fail` (halt the pipeline).

For more control over retry behavior:

```yaml
steps:
  research:
    agent: researcher
    retry:
      max: 3
      backoff: exponential     # none | linear | exponential (default: none)
    on-error: skip
    next: spec
```

### Harness-level resilience

```yaml
resilience:
  timeout: 1h                 # max time for the entire harness run (default: none)
  checkpoint: true            # enable checkpoint/resume on failure (default: false)
```

## Coordination patterns

The spec supports four coordination patterns for steps.

### Pipeline

Sequential steps connected by `next:`. The simplest and most common pattern.

```yaml
steps:
  research:
    agent: researcher
    next: spec

  spec:
    agent: spec-writer
    next: plan

  plan:
    agent: planner
```

### Router

One agent classifies input, output maps to the next step.

```yaml
steps:
  classify:
    type: router
    agent: classifier
    routes:
      feature: research
      bug: bug-pipeline
      refactor: refactor-pipeline
```

### Parallel

Multiple branches execute simultaneously.

```yaml
steps:
  implement:
    type: parallel
    branches:
      frontend: frontend-impl
      backend: backend-impl
      tests: tests-impl
    merge: append
    next: code-review

  frontend-impl:
    agent: frontend-dev
    eval:
      - metric: tests-pass
      - metric: lint-pass
    max-iterations: 3

  backend-impl:
    agent: backend-dev
    eval:
      - metric: tests-pass
      - metric: coverage
        pass: 80%
    max-iterations: 3

  tests-impl:
    agent: test-dev
    eval:
      - metric: tests-pass
    max-iterations: 3
```

Note how eval + max-iterations on each branch step replaces the need for a separate eval-loop pattern. The branches are named top-level steps, keeping indentation flat.

### Orchestrator

An agent dynamically spawns sub-agents from a pool. The harness defines constraints, the agent decides what to spawn.

```yaml
steps:
  research:
    type: orchestrator
    agent: researcher
    pool: [web-search, code-search, doc-search]
    max-agents: 5
    timeout: 10m
    next: spec
```

The orchestrator is the only pattern where the graph is not fully known at parse time. The agent builds the graph at runtime within the constraints the harness defines.

## Cross-cutting concerns

Evals, hooks, observability, and security can be applied at any level:

- **Global** — applies to all steps
- **Per-step** — overrides or extends global

Per-step config merges with global (additive, not replacing).

```yaml
# Global
observability:
  tracing: langfuse/v1

hooks:
  on-error: notify-slack

security:
  budget:
    max-tokens: 100000

steps:
  spec:
    agent: spec-writer
    # Per-step eval
    eval:
      - metric: llm-judge
        type: llm
        prompt: "Is this spec complete?"
        pass: 0.8
    max-iterations: 3
    # Per-step hook (adds to global, does not replace)
    hooks:
      after-step: ./scripts/notify.sh
    next: plan
```

## Full example

A Jira-triggered feature pipeline with routing, orchestration, parallel implementation, eval loops, and human gates.

```yaml
harnessfile: "0.1"
name: jira-feature-pipeline

trigger:
  event: ticket-created
  filter: "project = ENG AND type = Story"
  provider: jira/v1

observability:
  tracing: langfuse/v1

security:
  guardrails:
    output: [pii-scrub]
  budget:
    max-tokens: 500000
    max-cost: "$10.00"

memory:
  backend: postgres/v1
  scope: thread

resilience:
  timeout: 2h
  checkpoint: true

agents:
  classifier:
    model: ${FAST_MODEL:-anthropic/claude-haiku-4-5}
    instructions: Classify the Jira ticket as feature, bug, or refactor.

  researcher:
    model: ${DEFAULT_MODEL:-anthropic/claude-sonnet-4-6}
    instructions: Research the problem space thoroughly.

  web-search:
    model: ${DEFAULT_MODEL:-anthropic/claude-sonnet-4-6}
    instructions: Search the web for relevant information.
    tools:
      - mcp: ./tools/web-search.json

  code-search:
    model: ${DEFAULT_MODEL:-anthropic/claude-sonnet-4-6}
    instructions: Search the codebase for relevant patterns.
    tools:
      - mcp: ./tools/code-search.json

  spec-writer:
    model: ${DEFAULT_MODEL:-anthropic/claude-sonnet-4-6}
    instructions: Write a detailed technical spec.

  planner:
    model: ${DEFAULT_MODEL:-anthropic/claude-sonnet-4-6}
    instructions: Create an implementation plan with milestones and risks.

  frontend-dev:
    model: ${DEFAULT_MODEL:-anthropic/claude-sonnet-4-6}
    instructions: Implement frontend changes following React patterns.
    skills:
      - ./skills/coding.md
      - ./skills/code-review.md

  backend-dev:
    model: ${DEFAULT_MODEL:-anthropic/claude-sonnet-4-6}
    instructions: Implement backend changes following our API patterns.
    skills:
      - ./skills/coding.md
      - ./skills/code-review.md

  test-dev:
    model: ${DEFAULT_MODEL:-anthropic/claude-sonnet-4-6}
    instructions: Write comprehensive tests for the implementation.
    skills:
      - ./skills/coding.md

  merger:
    model: ${DEFAULT_MODEL:-anthropic/claude-sonnet-4-6}
    instructions: Merge all branches and resolve conflicts.
    skills:
      - ./skills/coding.md

steps:
  classify:
    type: router
    agent: classifier
    routes:
      feature: research
      bug: bug-pipeline
      refactor: refactor-pipeline

  research:
    type: orchestrator
    agent: researcher
    pool: [web-search, code-search]
    max-agents: 5
    timeout: 10m
    next: spec

  spec:
    agent: spec-writer
    eval:
      - metric: llm-judge
        type: llm
        prompt: "Is this spec complete and actionable?"
        pass: 0.8
    max-iterations: 3
    next: plan

  plan:
    agent: planner
    next: plan-review

  plan-review:
    type: gate
    approve: human
    provider: slack/v1
    channel: ${APPROVAL_CHANNEL:-#approvals}
    timeout: 1h
    fallback: reject
    next: implement

  implement:
    type: parallel
    branches:
      frontend: frontend-impl
      backend: backend-impl
      tests: tests-impl
    merge: synthesize
    next: code-review

  frontend-impl:
    agent: frontend-dev
    eval:
      - metric: tests-pass
      - metric: lint-pass
    max-iterations: 3

  backend-impl:
    agent: backend-dev
    eval:
      - metric: tests-pass
      - metric: coverage
        pass: 80%
    max-iterations: 3

  tests-impl:
    agent: test-dev
    eval:
      - metric: tests-pass
    max-iterations: 3

  code-review:
    type: gate
    approve: human
    provider: slack/v1
    channel: "#code-review"
    timeout: 2h
    fallback: reject
    next: merge

  merge:
    agent: merger
```

## v0.1 scope

### In scope

- Harness spec with steps, agents, and coordination patterns (router, pipeline, parallel, orchestrator)
- Skills as external SKILL.md file references, following the established convention
- Gates (human approval with provider, channel, timeout, fallback)
- Eval on any step with optional retry loop (eval + max-iterations)
- Data flow between steps (output schema, context selection, parallel merge)
- Error handling (retry, timeout, on-error per step; harness-level resilience)
- Variable substitution (`${VAR:-default}`)
- Security primitives (guardrails, budget, audit)
- Hooks at global and per-step level
- Trigger definition with provider
- Observability with sampling and level control
- Memory with scope and type
- Inline provider references with shorthand
- Built-in simple agent spec as default provider
- Support for external agent formats via providers (oracle-agent-spec, crewai, a2a, etc.)
- JSON Schema for validation

### Out of scope (future versions)

- Runtime implementation / reference runtime
- Provider SDK / provider development kit
- Agent-to-agent communication protocol (use A2A)
- Tool protocol (use MCP)
- Authentication / secrets management (credentials use ${VAR} — no separate interface)
- Versioning and migration between spec versions
- Visual editor / GUI tools
- Top-level provider registry (providers are inline)
- Composability / imports / multi-file harnesses
- Dynamic fan-out / map-reduce pattern
- Provider version pinning / lockfile
