# Harnessfile Spec v0.2 — Draft

## What is this?

Harnessfile is an open, vendor-neutral specification for AI agent **harnesses** — the operational
scaffolding around agents: triggers, gates, routing, squads, hooks, evals, memory, security, and
observability. The harness owns the graph and the rules — not the agent internals.

Since v0.2, **the spec is a directory**, not a single file. A harness is defined by the `.agents/`
directory in a repository:

```
.agents/
├── harness.yaml            # the harness — runtimes, triggers, gates, graph, routing, targets
├── agents/<slug>.md        # role cards — Markdown + YAML frontmatter
├── skills/<name>/SKILL.md  # Agent Skills open standard, adopted as-is
└── squads/<slug>.md        # leader + members + orchestration instructions
```

The definition is versioned, reviewed, and diffed like code. Coding-agent CLIs are **runtime
providers**; platforms and deployment environments are **targets**. `harnessfile up` dispatches
tasks to local runtimes such as Claude Code and Codex. `harnessfile sync` compiles/pushes the same
portable definition to targets such as Multica, which resolve it to managed runtime instances.

### What changed since v0.1 (the pivot)

v0.1 defined a single root YAML file with agents inline. v0.2 pivots to the `.agents/` directory
because the industry converged on file-based entities:

- **AGENTS.md** won project guidance (Linux Foundation / AAIF governed) — adopted as-is.
- **Agent Skills (SKILL.md)** won skills (~45 tools) — adopted as-is.
- **`.agents/skills/`** is read natively by Codex, Cursor, and Gemini CLI.
- **Markdown + YAML frontmatter** is the plurality subagent format (Claude Code, Cursor, Gemini CLI).
- The **harness layer** — triggers, gates, squads, routing, ownership — has no standard. That is
  what `harness.yaml` specifies.

Everything below the entity layer carries over from v0.1: the provider model, the unified graph
(triggers and outputs as nodes, polymorphic `next`), gates, evals, hooks, variables, data flow,
error handling, security, memory, and observability. See D39–D49 in `decisions.md`.

## Design principles

1. **Adopt what won, specify what didn't.** SKILL.md and AGENTS.md are used unchanged. The spec adds
   only the layers with no standard: the agent role card, the squad, and the harness itself.
2. **Defaults over config.** Every field has a sensible default. A minimal harness is a few lines.
3. **Progressive disclosure.** Start with the minimum. Add fields, providers, and overrides only as
   complexity demands.
4. **Extension surfaces are providers; agent transports are protocols.** Gates, evals, triggers,
   memory, observability, targets, and harness engines are provider-backed. Runtime profiles name
   coding-agent protocol families and are resolved to concrete instances by execution targets.
5. **Definition is portable; operations belong to the environment.** Git owns identity, instructions,
   skills, and structure. Each target owns its operational config (model placement, concurrency,
   secrets) after bootstrap. Secrets are never in the repo.

## Minimal example

One agent, one scheduled trigger. Two files:

```yaml
# .agents/harness.yaml
harnessfile: "0.2"
name: sentry-triage

runtimes:
  claude:
    protocol: claude-code/v1

triggers:
  hourly-sweep:
    schedule: "0 * * * *"
    prompt: Run a Sentry triage sweep. File genuine bugs only.
    next: triage
steps:
  triage:
    agent: triager
```

```markdown
<!-- .agents/agents/triager.md -->
---
name: triager
description: Triages Sentry issues into actionable bug reports.
runtime: claude
model: claude-sonnet-4-6
---
You triage Sentry issues. Deduplicate by issue id, ignore noise, file genuine bugs to the backlog.
```

## Entities

### Agents — `agents/<slug>.md`

Markdown + YAML frontmatter. The body is the system prompt. Compatible with the Claude Code /
Cursor / Gemini CLI subagent convention.

```markdown
---
name: engineer                # slug, required
description: Implements an approved plan and opens or updates the linked PR.  # required
runtime: codex                # portable runtime profile — targets may own this (D52)
model: gpt-5.5-codex          # opaque runtime-specific default
thinking-level: high          # optional runtime-specific reasoning/effort level
tools: [github, playwright]   # MCP servers / tools (optional)
skills: [ponytail, feature]   # skill names resolved in skills/ (optional)
---
# Role
You implement approved plans with minimal blast radius...
```

Frontmatter keys beyond the spec are allowed under a target namespace (e.g. `multica.display_name`)
and are passed through to that target on sync.

External agent formats remain available via providers (`provider: oracle-agent-spec/v1`, etc.).
The Markdown role card is simply the built-in agent provider, loaded by default.

### Skills — `skills/<name>/SKILL.md`

The [Agent Skills](https://agentskills.io) open standard, unchanged. The harness references skills
by name; the runtime/target loads them according to the standard's own rules. Supporting files
(`scripts/`, `references/`, `assets/`) travel with the skill directory.

### Squads — `squads/<slug>.md`

A squad is a leader agent plus members, with the leader's orchestration instructions as the body.

```markdown
---
name: development
description: Researches, plans, implements, and tests features and fixes.
leader: pm                    # agent slug, required
members:                      # agent members only — humans belong to targets
  - agent: pm
    role: Project manager, team leader
  - agent: researcher
    role: Gathers code, prior-decision, and web context
  - agent: engineer
    role: Implements the plan
---
# How the Development squad runs
Route by two independent scores, risk and ambiguity...
```

**Squads are agent-compatible**: a squad can be used anywhere an agent can — as a graph step, a
trigger target, or a member of another squad. The leader orchestrates members internally according
to its instructions; the graph does not model the squad's internals. This is the orchestrator
coordination pattern (it replaces v0.1's `type: orchestrator` step).

The explicit graph and leader orchestration coexist. Both of these are valid harnesses:

```yaml
# graph-first: the harness owns routing
steps:
  plan: { agent: planner, next: plan-review }
  plan-review: { type: gate, approve: human, provider: slack/v1, next: implement }
  implement: { agent: engineer }

# squad-first: the leader owns routing, the harness owns entry/exit and rules
triggers:
  issue-assigned: { provider: jira/v1, next: dev-squad }
steps:
  dev-squad: { squad: development }
```

## harness.yaml

### Top-level keys

```yaml
harnessfile: "0.2"        # spec version, required
name: string              # harness name, required
runtimes: map             # portable coding-agent runtime profiles (see Runtimes)
triggers: map             # entry nodes (may also be declared in steps with type: trigger)
steps: map                # the graph
targets: map              # sync targets and ownership (see Targets & ownership)
observability: object     # global, see interfaces
security: object
memory: object
resilience: object
hooks: object
```

### Triggers

Triggers are entry nodes of the graph. A harness can have multiple triggers with different shapes.
`triggers:` is sugar for steps with `type: trigger`.

```yaml
triggers:
  issue-assigned:
    provider: jira/v1
    event: issue-assigned
    filter: "project = ENG"
    output: { issue_id: string, title: string, description: string }
    next: development

  hourly-sentry:
    schedule: "0 * * * *"        # cron — makes this a scheduled trigger
    timezone: America/Sao_Paulo
    prompt: ./autopilots/sentry-triage.md   # inline string or path to a Markdown prompt
    next: triage

  deploy-webhook:
    provider: webhook/v1         # webhook URLs/secrets are target-owned, never in the repo
    output: { payload: object }
    next: development
```

A scheduled trigger with a `prompt` is the spec's form of an **autopilot** (Multica) or scheduled
agent run. Prompt files conventionally live in `.agents/autopilots/`, but any path works — the spec
has one concept, the trigger.

### Steps and the graph

Everything is a node; `next` defines edges and is polymorphic:

```yaml
next: step-name          # single edge — sequential
next: [a, b, c]          # parallel fan-out
# omit next              # end of path (or use type: output)
```

Fan-in is implicit — a step waits for all incoming edges and receives their outputs appended
(custom merge logic = use an agent step). Step types:

```yaml
steps:
  implement:
    agent: engineer            # agent step (default type) — agent: or squad:
    next: review

  dev-squad:
    squad: development         # squad step — leader orchestrates internally

  classify:
    type: router               # one agent classifies, output maps to next step
    agent: classifier
    routes: { feature: research, bug: bugfix }

  plan-review:
    type: gate                 # human approval checkpoint
    approve: human
    provider: slack/v1
    channel: "#approvals"
    timeout: 1h
    fallback: reject           # reject | approve | escalate
    next: implement

  done:
    type: output               # exit node
    input: { pr_url: string }
```

### Standard interfaces (carried from v0.1)

These interfaces are unchanged from v0.1 except where noted; see `spec/v0.1-draft.md` for extended
prose. All apply globally and per-step (per-step merges additively with global).

**Eval** — attach to any step; with `max-iterations`, the step retries until evals pass:

```yaml
eval:
  - metric: tests-pass                 # tests-pass | coverage | llm-judge | custom
    type: code                         # code | llm | human (default: code)
    pass: true                         # threshold (default: true)
max-iterations: 3
```

**Hooks** — lifecycle callbacks (`on-start`, `before-step`, `after-step`, `on-error`,
`on-gate-pending`, `on-gate-resolved`, `on-complete`); shorthand is fire-and-forget, full form
declares `can: [abort, modify]`. JSON on stdin/stdout, same contract as v0.1.

**Variables** — Docker Compose syntax, environment only: `${VAR}` (required),
`${VAR:-default}`. No expressions. Secrets are just env vars (never in the repo).

**Data flow** — full output forwarded by default; `output:` declares a schema, `context:` selects
what the step receives.

**Error handling** — per-step `timeout`, `retry` (count or `{max, backoff}`), `on-error:
fail | skip | continue`. Harness-level `resilience: { timeout, checkpoint }`.

**Security** — `guardrails` (input/output filters), `budget` (max-tokens / max-cost),
`audit` (destination/level).

**Memory** — `backend` (provider), `scope: thread | shared | global`,
`type: checkpoint | conversation | semantic`, `ttl`.

**Observability** — `tracing` / `metrics` providers, `sampling`, `level`. OpenTelemetry-aligned
providers are recommended (the MCP 2026-07-28 revision deprecates protocol-level logging in favor
of OTel).

## Runtimes

Coding-agent execution has three layers (D53):

1. A **protocol family** defines the wire contract with a coding-agent CLI, such as Claude Code
   stream-json or Codex app-server JSON-RPC.
2. A portable **runtime profile** names a protocol and may declare a command name plus fixed,
   non-secret arguments shared by every instance of that profile.
3. A target-resolved **runtime instance** is a concrete executable environment with its own
   identity, availability, version, and discovered capabilities.

This surface is not a model API client: the runtime supplies the terminal, file operations,
sandbox, MCP, skills, sessions, and structured execution events. The built-in reference protocols
are Claude Code stream-json and Codex app-server.

`harness.yaml` declares portable profiles:

```yaml
runtimes:
  claude:
    protocol: claude-code/v1
  codex:
    protocol: codex-app-server/v1
```

An agent's `runtime` references a profile name. `model` is an opaque string interpreted by that
runtime; Harnessfile does not infer a model provider from it. `thinking-level` is also passed
through to the runtime and its allowed values are runtime/model-specific.

Profiles select a protocol family, never a concrete process or machine. Local `up` discovers the
command on `PATH`, probes its capabilities, and creates a local instance identity. A managed target
resolves the same profile to a compatible online instance. Concrete runtime IDs, executable paths
tied to one machine, credentials, and secrets are operational state and MUST NOT be committed. A
target that owns `runtime`, `model`, or `thinking-level` may replace the portable defaults after
bootstrap.

A runtime driver starts a session with a structured event stream, a final result, session identity,
and cancellation. Standard event categories are status, text, thinking, tool-use, tool-result, log,
warning, and error. The harness engine re-emits these as `runtime` execution events annotated with
the step and agent identity. A target MAY persist a native session ID, but MUST resume it only against the
same compatible runtime instance and workspace; otherwise it starts a fresh session. The reference
Codex driver falls back to a fresh thread when `thread/resume` rejects a stale or missing thread.
The local target keeps runtime state outside the repository and gives Codex a workspace-and-instance
isolated `CODEX_HOME`, seeded from the user's existing CLI authentication and configuration.
Drivers own protocol-critical launch flags (transport, stream format, session, model, and approval
mode where applicable). A conflicting profile argument MUST be ignored with a structured warning
rather than overriding the driver's wire contract.

The harness engine owns graph traversal, gates, retries, and checkpointing. It MUST NOT instantiate
or call model API chat clients on behalf of agents (D52).

## Targets & ownership

Targets are the environments the definition is synced to or executed on. The crux of v0.2:
**the definition is portable; each target owns its operational config.**

```yaml
targets:
  multica:
    provider: multica/v1
    owns: [model, runtime, thinking-level, concurrency, env, mcp] # target-owned operations
    # bootstrap-then-hands-off: on first push, owned fields are seeded from
    # portable defaults (e.g. the agent's model:) or the provider's defaults.
    # Subsequent syncs NEVER overwrite owned fields.

  claude-code:
    provider: claude-code/v1        # materializes .claude/ symlinks → .agents/

  codex:
    provider: codex/v1              # generates .codex/agents/*.toml from agents/*.md

  github:
    provider: github-agent-hq/v1    # generates .github/agents/*.md
```

Rules:

1. Fields not listed in `owns` are always synced from the repo — git wins.
2. Owned fields are written once at bootstrap, then never touched — the target wins.
3. Target-side-only concepts (runtime instance IDs, human squad members, webhook secret URLs,
   credentials) are never represented in the repo and never reconciled.
4. Sync is dry-run by default; `--apply` mutates.
5. Entity frontmatter under a target's namespace (e.g. `multica.display_name`) provides round-trip
   identity mapping.

## CLI

```
harnessfile validate                  # schema + graph checks
harnessfile sync --target <name>      # compile/push definition to a target (dry-run by default)
harnessfile sync --target <name> --apply
harnessfile up                        # headless orchestrator: listens to triggers, enforces
                                      # gates/evals/hooks, dispatches to coding-agent runtimes — bound to the
                                      # board/chat/VCS the team already uses
harnessfile down | logs | status      # runtime lifecycle (Docker Compose model)
```

`up` interprets the directory at runtime (no codegen) and supports concurrent runs isolated per
thread, with gates suspending individual runs via checkpointing — semantics unchanged from v0.1
(D35–D38). LangGraph is the temporary reference graph/checkpoint engine; Claude Code stream-json
and Codex app-server are the first runtime protocols. LangGraph never instantiates the agents'
models (D52–D53).

## Compatibility

- **AGENTS.md** — orthogonal and complementary; Harnessfile does not replace or wrap it.
- **Agent Skills / SKILL.md** — adopted verbatim, including supporting files.
- **Subagent conventions** — `agents/*.md` is directly loadable by Claude Code (via symlink),
  Cursor, and Gemini CLI; Codex requires TOML generation (a sync target).
- **MCP** — tools on agents reference MCP servers; gate/HITL semantics will track the MCP
  2026-07-28 MRTR pattern once final.
- **A2A** — a future provider surface for cross-org squad members (out of scope for v0.2).
- **Oracle Agent Spec** — external agent definitions via provider, as in v0.1.

## Full example

An AltaVox-shaped development harness (see `examples/` for the complete version with all role cards):

```yaml
# .agents/harness.yaml
harnessfile: "0.2"
name: altavox-development

runtimes:
  claude: { protocol: claude-code/v1 }
  codex: { protocol: codex-app-server/v1 }

observability:
  tracing: otel/v1

security:
  budget: { max-cost: "$50.00" }

triggers:
  issue-assigned:
    provider: multica/v1          # or jira/v1, linear/v1, github/v1 — same shape
    event: issue-assigned
    next: development

  sentry-sweep:
    schedule: "0 * * * *"
    timezone: America/Sao_Paulo
    prompt: ./autopilots/sentry-triage.md
    next: sentry-triage

steps:
  development:
    squad: development            # PM leads; risk×ambiguity routing lives in the squad body

  sentry-triage:
    agent: sentry-triager

targets:
  multica:
    provider: multica/v1
    owns: [model, runtime, thinking-level, concurrency, env, mcp]
  claude-code:
    provider: claude-code/v1
  codex:
    provider: codex/v1
```

## v0.2 scope

### In scope
- The `.agents/` directory layout: `harness.yaml`, `agents/`, `skills/`, `squads/`
- Agent role cards (Markdown + frontmatter) and squads (agent-compatible orchestrator nodes)
- Portable coding-agent runtime profiles; local Claude Code and Codex protocol drivers
- Unified graph with triggers (incl. scheduled + prompt), gates, routers, outputs
- Targets with `owns` ownership and bootstrap-then-hands-off sync semantics
- All v0.1 interfaces: evals, hooks, variables, data flow, error handling, security, memory, observability
- CLI: `validate`, `sync` (Multica, Claude Code, Codex, GitHub Agent HQ), `up` (local coding-agent runtimes plus Jira/Linear/GitHub/Slack integrations)

### Out of scope (future versions)
- Cross-repo composition / registries of harnesses
- Dynamic fan-out (map-reduce from runtime state)
- Provider version pinning / lockfile
- A2A cross-org squad members
- Distributed execution of `up` (remote workers, task queues)
