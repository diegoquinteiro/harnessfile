# Harnessfile Spec v0.2 — Draft

## Status

Draft. Additive over v0.1 — every v0.1 Harnessfile is also a valid v0.2
Harnessfile. v0.2 adds vocabulary so authors can express workflows that
target compile-time runtimes like Archon (`coleam00/Archon`) without
dropping down to runtime-specific escape hatches.

## What's new

v0.2 extends v0.1 in five orthogonal ways:

1. **Inline execution modes on steps** — `prompt:`, `bash:`, `command:`,
   `loop:` let a step carry its own work without referencing a pre-defined
   agent.
2. **Backward edges** — `depends_on:` as an alternative to forward `next:`,
   for authors who prefer the DAG-dependency style used by GitHub Actions and
   Archon.
3. **Explicit fan-in modes** — `wait-for: all | any | all-done | any-done`
   (implicit `all` remains the default per D33).
4. **Compile providers** — a new kind of provider that emits target files
   (e.g., Archon YAML) instead of executing the harness itself.
5. **Provider passthrough** — top-level and per-step fields that aren't in
   the core spec vocabulary flow into a `raw:` bag for provider-specific
   consumption. This lets authors express Archon-native constructs
   (`approval`, `skills`, `mcp`, `hooks` in Claude Code format, `context:
   fresh`, `idle_timeout`, …) without bloating the core spec.

v0.2 also changes one parse-time behavior:

- **Environment variable substitution syntax**. v0.1 used `${VAR}` /
  `${VAR:-default}`, which collides with POSIX shell parameter expansion
  inside `bash:` bodies. v0.2 switches to the unambiguous `${{ VAR }}` /
  `${{ VAR:-default }}` form (GitHub Actions style). v0.1 substitution is
  preserved for v0.1 files based on the declared `harnessfile:` version.

Everything else — hooks, observability, memory, security, resilience, gates,
routers, orchestrators, eval loops — is unchanged from v0.1.

## Minimal example

Still 4 lines. v0.2 makes `agents:` optional when steps use inline execution:

```yaml
harnessfile: "0.2"
steps:
  hello:
    command: archon-assist
```

## Design principles

Unchanged from v0.1:

1. **Flat over nested** — max 3 levels of indentation.
2. **Defaults over config** — works with the minimum.
3. **Progressive disclosure** — start small, add only what complexity
   demands.
4. **Interfaces over implementations** — the spec defines contracts,
   providers implement.
5. **The spec is the graph, providers are the nodes**.

## New: inline execution modes

A step declares its work via one of four mutually-exclusive fields:

```yaml
steps:
  # 1. `agent:` — reference a pre-defined agent (v0.1, unchanged)
  research:
    agent: researcher

  # 2. `prompt:` — inline prompt for an ad-hoc agent call, no agent def needed
  classify:
    prompt: |
      Classify the issue below as bug, feature, or refactor.
      Issue: $fetch.output
    model: haiku
    allowed-tools: []
    output-format:
      type: object
      properties:
        type: { type: string, enum: [bug, feature, refactor] }
      required: [type]

  # 3. `bash:` — deterministic shell execution
  fetch:
    bash: |
      gh issue view "$ARGUMENTS" --json title,body
    timeout: 30000

  # 4. `command:` — reference to an external command file (Archon-native)
  investigate:
    command: archon-investigate-issue
    context: fresh
```

Plus `loop:`, which is orthogonal to the four above and can wrap an `agent:`,
`prompt:`, or `command:` step (see **Loop block**).

### New per-step fields

All optional:

| Field | Purpose |
|---|---|
| `depends_on: [step, ...]` | Backward edges — alternative to forward `next:`. |
| `when: "expression"` | Opaque expression string evaluated by the runtime. Harnessfile does not parse it. Archon evaluates `$node.output[.field] == 'value'`-style expressions. |
| `wait-for: all \| any \| all-done \| any-done` | Fan-in mode when multiple steps converge. See **Wait-for**. |
| `model:` | Per-step model override (falls through to agent or top-level default). |
| `allowed-tools: [Name, ...]` | Whitelist tools available to this step. Empty list = no tools. |
| `denied-tools: [Name, ...]` | Blacklist tools for this step. |
| `output-format:` | Structured output contract. Accepts JSON Schema; when `validate: true`, runtime parses and validates the agent's output as JSON. |
| `context:` | Opaque context directive for the runtime (Archon uses `fresh` to force a new session). |

All new fields compose with v0.1 fields (`timeout`, `retry`, `on-error`,
`eval`, `max-iterations`, per-step `hooks`, per-step `provider`).

## New: `loop:` block

Terminates by agent sign-off, not by metric. Orthogonal to `eval:` (which
retries based on metric thresholds). A step may have both:

```yaml
steps:
  implement:
    agent: implementer
    loop:
      prompt: |
        Implement the next task. When all tasks are done, output <promise>COMPLETE</promise>.
      until: COMPLETE
      max-iterations: 15
      fresh-context: true      # reset conversation each iteration
      interactive: false        # pause for human input between iterations
      gate-message: ""          # prompt shown to the human when interactive
```

Field semantics:

- **`until:`** — plain string marker. Runtime looks for
  `<promise>{until}</promise>` in the agent's output; match ends the loop.
- **`until-bash:`** — alternative: bash script; exit-0 ends the loop.
- **`max-iterations:`** — safety bound.
- **`fresh-context:`** — start a new thread per iteration (agent re-reads
  state from disk).
- **`interactive:`** — suspend after each iteration; inject human input as
  `$LOOP_USER_INPUT` (opaque runtime variable, provider-specific).

## New: `depends_on` as backward edges

v0.1 uses `next:` for forward edges. v0.2 accepts `depends_on:` on a step
as an alternative (and complement). Both forms can coexist in the same
harness:

```yaml
steps:
  a:
    command: foo

  b:
    command: bar
    depends_on: [a]          # b runs after a

  c:
    command: baz
    depends_on: [b]          # DAG-dependency style
```

A step with `depends_on: [x, y]` fans in from both `x` and `y`. By default,
it waits for all of them to succeed (implicit `wait-for: all`).

## New: `wait-for` fan-in modes

When multiple steps converge on a single target, the target's `wait-for:`
field controls when it runs:

| Value | Meaning | Archon equivalent |
|---|---|---|
| `all` (default) | Wait for all dependencies to succeed. | `all_success` |
| `any` | Run as soon as the first dependency succeeds. | `one_success` |
| `all-done` | Wait for all dependencies to finish (success or failure). | `all_done` |
| `any-done` | Run as soon as the first dependency finishes. | *(no equivalent — compile providers warn)* |

`any-done` is included for completeness of the quadrant (how-many × cares-about-failure). Not every compile target supports it.

## New: provider passthrough (`raw:`)

Any field not in the core spec vocabulary — at both top-level and per-step —
is preserved verbatim in a `raw:` bag on the IR. This is how Archon-native
constructs flow through without being formalized in the spec:

```yaml
harnessfile: "0.2"
name: archon-refactor-safely
provider: claude               # archon-native top-level
model: sonnet                  # archon-native top-level default

steps:
  implement:
    command: archon-implement
    context: fresh              # archon-native: "new session"
    hooks:                      # Claude Code format, not v0.1 lifecycle hooks
      PreToolUse:
        - matcher: "Write|Edit"
          response: { ... }

  gate:
    approval:                   # archon-native interactive gate
      message: "Review and respond"
      capture_response: true
    depends_on: [implement]
```

The parser puts anything unrecognized into `raw`; compile providers consume
the bag and emit the right target-specific field. For the `hooks:` field
specifically, the parser disambiguates: if all keys are v0.1 lifecycle
events (`on-start`, `before-step`, `after-step`, `on-error`,
`on-gate-pending`, `on-gate-resolved`, `on-complete`), it's parsed as a v0.1
`HooksDef`. Otherwise (Claude Code format, etc.) it flows to `raw`.

## New: compile providers

v0.1 had a single provider contract (`HarnessProvider`) designed for runtime
execution (`compile(ir) → CompiledHarness` with `createRun`, `resumeRun`,
etc.). v0.2 introduces a second contract, `CompileProvider`, for providers
that translate IR to a target format at build-time:

```ts
interface CompileProvider {
  target: string;                    // e.g., "archon/v1"
  displayName: string;
  compile(ir: Harnessfile): CompileResult;
}

interface CompileResult {
  files: CompileFile[];              // path + content
  warnings: Warning[];               // structured
}

interface Warning {
  severity: "info" | "warning" | "error";
  code: string;                      // stable machine-readable
  message: string;
  path?: string;                     // IR path
  suggestion?: string;
}
```

Compile providers are:

- **Code generators**: they produce target YAML/JSON/source files.
- **Warning-first**: every feature they can't represent losslessly emits a
  structured `Warning` with a stable `code`. Tests assert on warning code
  sets; CI uses `--strict` to fail on non-info warnings.
- **Invoked via `harnessfile compile`**:

```bash
harnessfile compile my.harnessfile.yaml \
  --target archon/v1 \
  --out .archon/workflows/ \
  --strict
```

Options: `--target`, `--out` (omit → stdout), `--strict` (fail on non-info
warnings), `--json` (emit `<name>.warnings.json` alongside output).

The first compile provider shipped in v0.2 is `archon/v1`. The interface is
general — additional targets (CrewAI, LangFlow, …) fit the same contract.

## Environment variable substitution changes

v0.1 syntax, preserved for v0.1 files:

```yaml
# v0.1 file header
harnessfile: "0.1"
agents:
  x:
    model: ${MODEL:-anthropic/claude-sonnet-4-6}
```

v0.2 syntax — unambiguous with POSIX shell:

```yaml
# v0.2 file header
harnessfile: "0.2"
agents:
  x:
    model: ${{ MODEL:-anthropic/claude-sonnet-4-6 }}

steps:
  run:
    bash: |
      # This $VAR is passed verbatim to bash, not substituted by Harnessfile:
      DURATION=${DURATION:-150}
      MID_FRAME=$((DURATION / 2))
```

Substituter detects the declared `harnessfile:` version in a pre-parse
regex scan. v0.2 files use `${{ ... }}`; v0.1 files keep `${ ... }`. The
two syntaxes coexist in the same codebase without collision.

## Compile targets

### archon/v1

Target: Archon workflow YAML, per coleam00/Archon's
`.archon/workflows/defaults/` format.

Supported constructs:

| Harnessfile | Archon | Notes |
|---|---|---|
| `name`, `description` | `name`, `description` | top-level |
| `provider`, `model` (top-level) | `provider`, `model` | passed through |
| `steps.{id}` with `agent:` | `nodes[].prompt:` (instructions inlined) | |
| `steps.{id}` with `prompt:` | `nodes[].prompt:` | |
| `steps.{id}` with `bash:` | `nodes[].bash:` | |
| `steps.{id}` with `command:` | `nodes[].command:` | Archon-native |
| `steps.{id}` with `loop:` | `nodes[].loop:` | 1:1 mapping |
| `steps.{id}.next: [Y, Z]` | `nodes[Y].depends_on += [X]`, same for Z | inverted |
| `steps.{id}.depends_on` | `nodes[].depends_on` | direct |
| `steps.{id}.when` | `nodes[].when:` | opaque string |
| `steps.{id}.wait-for: any` | `nodes[].trigger_rule: one_success` | |
| `steps.{id}.wait-for: all-done` | `nodes[].trigger_rule: all_done` | |
| `steps.{id}.wait-for: any-done` | (fallback `one_success` + warning) | no Archon equivalent |
| `steps.{id}.output-format` | `nodes[].output_format` | JSON Schema |
| `steps.{id}.allowed-tools` | `nodes[].allowed_tools` | |
| `steps.{id}.denied-tools` | `nodes[].denied_tools` | |
| `steps.{id}.model` | `nodes[].model` | mapped via MODEL_MAP or passthrough |
| `steps.{id}.raw.*` | emitted verbatim | hooks, approval, skills, mcp, idle_timeout, context, … |

Warning codes:

- `model-not-mapped` — a model ID has no MODEL_MAP entry; passthrough.
- `skills-not-supported` — agent-level `skills:` (Archon uses node-level).
- `eval-not-supported` — `eval:` metrics don't translate.
- `feature-ignored` — observability / memory / security / v0.1 hooks /
  resilience have no Archon equivalent; dropped.
- `wait-for-any-done-unsupported` — `any-done` falls back to `one_success`.
- `orchestrator-not-supported` (severity: error) — Archon has no dynamic
  agent pool construct.
- `trigger-not-translated` / `output-not-translated` — Archon uses platform
  adapters rather than inline trigger/output nodes.
- `router-needs-structured-output` — `type: router` without `output-format`.

## v0.2 scope

### In scope

- Everything in v0.1 (unchanged).
- Inline execution modes (`prompt`, `bash`, `command`, `loop`).
- `depends_on` backward edges.
- `wait-for` fan-in modes.
- Per-step `model`, `allowed-tools`, `denied-tools`, `output-format`,
  `context`, `when`.
- Provider passthrough via `raw:`.
- `CompileProvider` contract and `harnessfile compile` command.
- `archon/v1` compile provider with round-trip parity for the 20 default
  workflows in `coleam00/Archon`'s `.archon/workflows/defaults/`.
- GitHub Actions–style env var substitution (`${{ VAR }}`).

### Out of scope (future versions)

- Runtime execution of `prompt`/`bash`/`command`/`loop` inside the LangGraph
  provider (`harnessfile up` works for v0.1 shapes; v0.2-only shapes compile
  via `harnessfile compile` but don't execute via `up`).
- Additional compile targets (CrewAI, LangFlow).
- Dynamic fan-out / map-reduce.
- Sub-harness inclusion (`harness:` step field — Open Item #1 still deferred).
- Runspace / worktree isolation as a first-class spec concept.
- Reverse compiler (Archon YAML → Harnessfile).
